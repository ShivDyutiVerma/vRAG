## Done

- Extracted the R-006 chunk-to-passage dedup fix out of `scripts/eval_chunking.py`'s inline copy
  into shared `score_hits`/`dedupe_doc_ids` in `src/vrag/retrieval/metrics.py`, unit-tested, so A3's
  new eval script can't reintroduce the same bug by forgetting to copy the fix.
- **A3 (retrieval mode) — ran dense/sparse/hybrid+RRF against the frozen 500-query held-out set**,
  reusing the already-persisted index (no rebuild). Result was a genuine surprise: dense-only
  (Recall@5=0.652) beat hybrid+RRF (0.604), which beat sparse-only (0.428) — the opposite of
  `docs/TECH_MENU.md`'s own "hybrid is the 2026 production default" framing and
  `AGENT_BUILD_SPEC.md`'s assumed Phase-3 exit criterion. Verified it wasn't a wiring bug before
  writing it up: confirmed both indexes return best-first as RRF requires, confirmed the dedup path
  is shared and correct across all three modes. Root cause: BM25 is comparatively weak on this
  machine-translated Hindi corpus, and naive equal-weight RRF has no way to discount a weaker lane —
  its lower-quality top ranks get the same fusion credit as dense's stronger ones.
- **A4 (rerank) — ran none/FlashRank/cross-encoder.** First attempt at FlashRank hung for ~20+
  minutes at a sustained ~28s/query rate before I killed it and investigated. Root-caused to two
  separate real problems: (1) `rerankers`' FlashRank backend needs a separate `flashrank` package
  not originally installed (fixed, new dependency R-011); (2) even after that, real corpus-length
  Hindi text took 9-14s/call on CPU-only `onnxruntime` — traced to no `onnxruntime-gpu` installed,
  ~500x TECH_MENU's own "sub-20ms" estimate (which was almost certainly benchmarked on short English
  candidates, not this model/language/length combination).
- Both rerankers turned out to **actively destroy quality**, not just fail to help — recall@5
  collapsed to 0.10 (FlashRank, n=30 sample) and 0.228 (cross-encoder, n=500) vs. 0.652 for `none`.
  This was surprising enough (much larger than any prior ablation gap) that I didn't trust it without
  query-level verification: wrote small diagnostic scripts that showed FlashRank's multilingual model
  saturates at ~1.000 for every Hindi candidate regardless of relevance (confirmed Hindi-specific —
  same model discriminates cleanly on short English text), and the cross-encoder — an English-only
  model — ranks an obviously-correct short Hindi answer *below* clearly irrelevant candidates. Both
  are genuine model/language-fit failures, not bugs in the harness.
- **Wired the A3/A4 winners into production**, but paused first: CLAUDE.md's hot-path invariants and
  `AGENT_BUILD_SPEC.md` line 625 both assumed hybrid would win, so switching the default is a real
  deviation from written project instructions, not just an internal implementation detail. Asked the
  user directly rather than deciding either way unilaterally; confirmed ship dense-only, keep hybrid
  mode implemented and tested but off by default. Applied: `HybridRetriever` now takes a
  `retrieval_mode` param (dense/sparse/hybrid); dense mode skips BM25 entirely; CLAUDE.md's invariant
  text and `interface.py`'s docstring both updated to state the new default and point to the ADR.
- Found and verified a real, useful side effect of the switch: `RetrievedChunk.score` moves from
  RRF-fused values (~0.008-0.033, structurally always below G3's `TAU=0.35`) to raw cosine similarity
  (~0.3-0.95, the scale G3's own docstring says `TAU` was calibrated for). Confirmed with a live
  `/ask` call, not just score-range math: the still-abstaining local test's `refusal_reason` moved
  from what would've been a structurally-guaranteed `TAU` failure to the `MARGIN` (ambiguity) check
  instead — a real, if still uncalibrated, signal. Flagged for Workstream P (`docs/RISKS.md` P-R18)
  rather than touched, since `g3_confidence.py` is their module.

## Surprises & learnings

- The biggest lesson of the session: **when a result is much larger than any plausible noise floor,
  that's exactly when it deserves the most scrutiny, not the least.** A3's ~5pp regression and A4's
  ~55pp collapse could both have been shipped as "interesting findings" without the query-level
  diagnostics — but the diagnostics are what turned "huh, weird" into "verified, here's the
  mechanism," which is the actual deliverable a decision trail needs.
- A measured ablation result can contradict a written project instruction (CLAUDE.md's hot-path
  invariant, the spec's assumed exit criterion) without either being wrong — the spec encoded an
  assumption made before any data existed; the data is now real. The right move wasn't to silently
  override the written rule, and it wasn't to silently defer to it over the evidence either — it was
  to surface the conflict and let the user decide, since only they know how much weight the original
  assumption should carry against measured reality.
- A background process reporting "completed" isn't always what it looks like: launching `nohup ... &`
  inside an already-backgrounded shell call double-backgrounds the real work, so the tool sees the
  *launcher* exit immediately while the actual Python process keeps running, untracked, in the
  background. Running the long command directly with the tool's own background flag (no `nohup`)
  fixed it.
