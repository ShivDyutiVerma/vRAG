## What I learned

- **A number measured in isolation and a number measured in the real deployment target can both be
  "true" and still disagree wildly** — my 727MB (a bare Python process on Windows via `tasklist`)
  and P's 446.8MB (the actual Docker image under Render's real memory limit) are both honest
  measurements of different things. Neither was wrong; they were answering different questions.
  Always ask "measured where, measured how" before treating two numbers as comparable.
- **Steady-state memory and peak memory during initialization are a different question**, and the
  gap between them can be the entire story. A service can fit comfortably once warmed up and still
  get OOM-killed every time it starts, if loading the model/index transiently needs more headroom
  than running it does. "It works once it's running" and "it works" are not the same claim.
- **When a "bounded cost" turns out to have a fixed floor, do the arithmetic before spending the
  budget on it.** R-020 originally framed corpus-shrink as a reasonable, boundable tradeoff. It
  wasn't, once the embedder's session cost turned out to be a fixed ~388MB regardless of corpus
  size — the real ceiling (83% cut needed) only showed up by fitting a real measured curve to the
  actual remaining budget, not by assuming "smaller corpus = proportionally smaller total."
  Cheap, targeted measurement (two subsampled indices, reusing already-computed FAISS vectors via
  `reconstruct()` instead of re-embedding) answered this in minutes instead of a full re-ablation.
- **Two independent sessions can converge on the same right answer without coordinating**, which
  looks like a discrepancy until you check both sides in full. The apparent RISKS.md conflict
  turned out to be two people already agreeing, just captured slightly differently in the doc at
  slightly different times.
