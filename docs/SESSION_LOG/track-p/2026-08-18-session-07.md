## Surprises & learnings

- "Verified live" is not one claim, it's several, and each only rules out the specific failure
  mode it actually tests. Every check I ran this session against the real URL was honest and
  correct for what it tested (G3's threshold, the circuit breaker's behavior, streaming's stall
  detection) — none of them would have caught retrieval being stubbed, because the stub's whole
  design goal (matching the real path's output shape exactly) is what let it hide in plain sight
  behind a working-looking pipeline. A "does the system work end-to-end" check and a "is this
  specific stage using its real implementation" check are different questions, and passing the
  first doesn't imply the second.
- A tradeoff question can have an answer that's obviously true once stated ("corpus-only can't
  work, the embedder's own overhead alone exceeds the budget") but isn't obvious from the raw
  numbers alone until someone does the subtraction. Worth checking the arithmetic on a measured
  finding before presenting options built on top of it, rather than assuming three parallel options
  are equally real just because they were all named as candidates.
- Building a defensive fallback fix *before* staging a risky-looking infrastructure change (rather
  than after, if something breaks) turned "download an index artifact into a container that can't
  yet use it" from a real regression risk into a safe, verifiable no-op. Worth remembering as a
  general pattern: when a change is only *supposed* to be inert, prove it by testing the exact
  failure path it depends on staying inert, not just the happy path.
