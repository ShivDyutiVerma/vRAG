## Goal

## Done

- Before writing any client-facing streaming code, probed the live Sarvam API with the real
  schema/prompt to measure actual time-to-first-answer-content (not raw TTFT), since the schema's
  reasoning-before-answer field order means `reasoning` has to finish before `answer` starts.
  Single-chunk contexts streamed and completed fine. A realistic 5-chunk context (closer to real
  k=5 retrieval, forcing genuine discrimination between a correct passage and 4 distractors)
  exposed two real, previously-undiscovered Sarvam bugs.
- **Bug 1:** our own schema's `reasoning` field is unconstrained, and `reasoning_effort: null`
  doesn't touch it — that flag only disables a separate, hidden CoT mechanism. With a harder
  context, the model sometimes wrote a full paragraph (or a long numbered chain-of-thought) into
  `reasoning`, consuming the whole `max_tokens=512` budget before `answer` was ever reached. Fixed
  with an explicit "keep it to one short sentence" system prompt instruction. Verified: reasoning
  field length dropped ~5-8x, successful-call latency dropped from ~2.2-2.7s to ~1.0-1.2s.
- **Bug 2, found only after fixing bug 1:** even with brief reasoning, several runs still failed —
  differently. The model correctly completes `reasoning` and `answer`, then never continues to the
  final field (`cited_chunk_ids_csv`) or closes the JSON object — pads whitespace toward
  `max_tokens` instead. Same *symptom* as the already-documented P-R15 array-field bug, confirmed
  *distinct* cause: `cited_chunk_ids_csv` has been a plain string since P-013, and it still
  happens. P-R15's original fix addressed a real cause, not the only one.
- Switched `sarvam_llm.py` from a single blocking POST to `stream: true` + SSE consumption
  specifically to catch bug 2 fast: track consecutive whitespace-only/empty content deltas, abort
  after 20 in a row. Chose 20 from real data — legitimate JSON formatting whitespace (the
  newline+indent between fields) never exceeded 2 consecutive chunks in any successful run
  observed; the bug produces hundreds. Wired the abort into `generate()`'s existing repair-retry
  loop (same "2 attempts total" shape, no new retry machinery needed).
- 6 new unit tests using `httpx.MockTransport` (no live network): content reconstruction, tolerates
  legitimate whitespace, raises at the threshold, empty deltas count too, and `generate()`'s
  retry-then-succeed / retry-then-give-up paths. Then verified live: 3 runs against the real API
  with a realistic context — 2/3 stalled on *both* attempts (a real, non-rare rate) but were each
  detected and handled in ~2.2-2.6s instead of the 4-60s+ this would have taken before; Track A
  correctly covered every failure, every time.
- 83/83 tests green (77 pre-existing + 6 new). `ruff`/`mypy` clean.

  narrative — it made failures cheap, not rare.

## Surprises & learnings

- Measuring before building paid off directly: the original plan was "add client-facing streaming
  for a nicer UX," but the very first real probe (not a mock, not an assumption) redirected the
  whole session toward a reliability bug that mattered more than the UX question it was sent to
  answer. Worth remembering: a live probe against the real dependency, run *before* committing to
  an implementation plan, can change what the actual right feature to build even is — not just how
  to build the one already decided on.
- A single flag (`reasoning_effort: null`) can look like it fully solves a class of problem
  ("reasoning eating the token budget") while actually only covering one specific mechanism of it.
  The model had its own, separate way to produce unbounded reasoning-like content — inside a field
  *we* defined in *our* schema — that the provider's own reasoning-control flag has no reason to
  know about, since from the provider's perspective that's just "content the caller asked for,"
  not "reasoning" in the sense the flag controls.
- The same observable symptom (whitespace padding to `max_tokens`) showing up again after the
  believed root cause (array-typed fields) had already been removed was a useful reminder that
  "isolated by removing X and watching the symptom disappear" only proves X was *a* sufficient
  cause in that one test, not the *only* one — especially for a symptom as generic as "stops
  producing real content." Worth re-testing an old "fixed" finding under new conditions (here: a
  harder, more realistic context) rather than assuming a prior fix's scope was complete.

## Numbers measured this session

Real (not fake-data) live-probe results, `sarvam-105b`, `strict: true` json_schema, 5-chunk
context, against the live Sarvam API (not committed as a script — throwaway scratchpad probes):
- Baseline system prompt: reasoning field length ~250-300 chars on success; 1/3 runs succeeded
  cleanly (~2.2-2.7s), 1/3 exhausted `max_tokens` inside an unbounded reasoning field
  (`finish_reason: "length"`, no `answer` key ever reached), 1/3 timed out entirely (30s, zero
  content).
- Brief-reasoning prompt: reasoning field length ~30-50 chars; across two further batches
  (3 runs + 6 runs), successful completions landed at ~1.0-1.2s, but a meaningful fraction (3/3 in
  the first batch, 1/6 timing out + otherwise fast in the second) still hit the whitespace-padding
  bug (bug 2) rather than the reasoning-budget bug (bug 1) — confirming the two bugs are distinct
  and the second isn't fixed by the first.
- Live pipeline verification with stall detection wired in (15s budget, 3 runs): 2/3 stalled on
  both attempts, detected and handled in 2205ms/2607ms; 1/3 hit a genuine zero-content network
  hang, correctly bounded by the existing timeout at 15003ms (the full budget).
