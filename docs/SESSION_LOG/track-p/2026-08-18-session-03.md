## Surprises & learnings

- A hanging (not erroring) API is a specifically nasty failure mode — it's silent, it doesn't
  trip obvious alarms, and without deliberately testing the "valid request against a broken
  backend" case (as opposed to just the "bad input" cases), it would have looked fine in every
  quick check and only shown up as mysterious slowness in the actual demo. Worth remembering: test
  the happy path against a *live* dependency specifically, not just against your own error
  handling for bad inputs.
- Scheduling something as "joint work, later" can smuggle in an assumption that turns out to be
  stale by the time "later" arrives — G3/G4 were scheduled around a blocker (no real retrieval
  scores) that R had already resolved a full day earlier. Worth re-checking the *reason* a
  dependency was declared, not just trusting the schedule that cited it.
- `min_viable_ms` as a pure pre-flight check is a subtle trap: it reads like a promise ("this
  stage costs at most X ms") but only enforces "we won't *start* this stage unless X ms are
  available" — nothing connects it to what happens once the stage is actually running. A
  deadline-propagation system needs both halves to be a real guarantee, and it's easy to build
  only the first half and believe you're done.
